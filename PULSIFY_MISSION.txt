PHASE 0 - SET UP THE TEAM
======================================================================
Reference: my MzansiAcademy repo (thabisosengane5-collab/MzansiAcademy-) has this

What each one is (so you build them correctly):
- AGENT (.claude/agents/<name>.md) = a separate worker with its own context, role and
  limited tools. It does one job and reports back. Read-only agents CANNOT edit files.
- SKILL (.claude/skills/<name>/SKILL.md) = a playbook the main Claude follows. The
  pipeline skill tells the main Claude which agent to call, in what order.

Agent file format (YAML frontmatter, then the instructions):
  ---
  name: researcher
  description: <when to use it - one or two lines>
  tools: Read, Grep, Glob, Bash, WebSearch, WebFetch
  model: sonnet
  ---
  <role, how to work step by step, rules, what the output looks like>

Model note: .claude/settings.json sets CLAUDE_CODE_SUBAGENT_MODEL=haiku. That's fine
for the builder, but the researcher and reviewer need stronger judgement. Set
`model: sonnet` on those two and check whether the env var overrides it. If it does,
tell me and suggest the change to settings.json. Don't change it yourself.

---------------------------------------------
AGENT 1: researcher   (always fires first)
---------------------------------------------
Tools: Read, Grep, Glob, Bash, WebSearch, WebFetch. Read-only: no Edit/Write.
Job: before any build work, find out the facts and write a BRIEF.
- For bugs: reproduce the problem, find the exact files, lines, tables and RLS policies
  involved, and state the root cause with evidence (not a guess).
- For outside questions (payments, animation libraries): search the web for CURRENT
  info. Prices, fees and requirements change, so cite a source URL and date for every
  claim. Prefer official docs over blogs.
- Output: a brief with the problem, evidence, root cause, recommended fix, files to
  touch, risks, and "what I could not confirm".
- Rule: if you're unsure, say so. Never invent fees, requirements or API behaviour.

---------------------------------------------
AGENT 2: builder
---------------------------------------------
Tools: Read, Grep, Glob, Bash, Edit, Write.
Job: implement exactly what the researcher's brief says, nothing more (CLAUDE.md
sections 2-3: simplicity, surgical changes).
Rules:
- Back up any big HTML file before editing it (cp file file.bak) and delete the
  backup before committing.
- Follow every hard rule in CLAUDE.md section 5 (getSB(), even backtick count, no broad
  regex edits, service key server-only, SA map bounds, mock data only as fallback).
- Supabase schema changes go in a new .sql file in db/ AND get applied through the
  migration tool. Never edit data in production without my OK.
- Hand off to the reviewer. Never merge or deploy.

---------------------------------------------
AGENT 3: reviewer
---------------------------------------------
Tools: Read, Grep, Glob, Bash. Read-only.
Job: review only what changed (git diff) against the brief.
Check, in this order:
  1. Correctness: does it actually fix the root cause? Are edge cases handled
     (signed out, no posts, deleted post, slow network)?
  2. Security: RLS policies on any table touched, user content escaped before
     innerHTML, no secrets in the diff
     (git diff | grep -iE "key|secret|token|password" and read the hits).
  3. CLAUDE.md hard rules.
  4. Simplicity: is there unneeded code?
Output: findings with file, line, problem, fix and severity
(BLOCKER / FIX / NIT). Say "PASS" only if there are no BLOCKER or FIX items.

---------------------------------------------
AGENT 4: designer   (UI, layout and animation)
---------------------------------------------
Tools: Read, Grep, Glob, Bash, Edit, Write.
Job: layout and visual work: the post card layout, settings page layout, and later the
character animation (Phase 4).
Rules:
- Phone-first. Most users are on cheap Android phones on mobile data. Design at 390px
  wide first, then check desktop.
- Match the existing Pulsify look (colours, fonts, spacing). Don't redesign what isn't broken.
- Take screenshots with Playwright at 390px and desktop and LOOK at them before
  handing off.
- Hand off to the reviewer. Never merge or deploy.

---------------------------------------------
AGENT 5: qa-tester
---------------------------------------------
Tools: Read, Grep, Glob, Bash. Read-only.
Job: test in a real browser (Playwright/Chromium) before anything is shown to me.
- Click through the changed flows at 390px and desktop, signed in AND signed out.
- Check: no console errors, no sideways scrolling, tap targets big enough, nothing
  hidden behind fixed bars, and data survives a page reload AND shows up for a second
  test user (this matters for posts and comments).
- Use .claude/RELEASE_CHECKLIST.md items where they apply.
- Output: PASS/FAIL per check, with details and screenshot paths. Say plainly what you
  could NOT test (Google sign-in, real payments, push notifications).

---------------------------------------------
SKILL 1: pulse-pipeline   (.claude/skills/pulse-pipeline/SKILL.md)
---------------------------------------------
Description: use for ANY bug fix, feature or UI change on Pulsify. Runs the team in
order and stops for the owner's approval.
Steps:
  1. researcher -> brief. If the job touches more than one area, show me the plan first.
  2. builder (code) and/or designer (layout/visual) -> implement from the brief.
  3. reviewer -> send every BLOCKER/FIX back to the builder or designer. Repeat until
     PASS, max 3 rounds, then ask me.
  4. qa-tester -> any FAIL goes back to whoever owns it.
  5. Approval -> show me: what changed in plain words, reviewer PASS, QA results,
     1-2 screenshots, the preview URL, and what wasn't tested.
  6. Ship -> claude/** branch, commit, push, draft PR. Merging to main = going live;
     only I say when (run ship-check first).
Ask me first, and don't decide alone, when: money is involved, user data could be
deleted, a third-party sign-up is needed, or the fix changes how the product works.

PHASE 2 - PAYMENT PROVIDER   (RESEARCH + RECOMMENDATION FIRST)
======================================================================
Situation: payment code is already written for Paystack (api/payments/index.js
webhook, lib/payouts.js transfers to organisers, subscriptions R220 organiser / R360
business). My problem is that I can't get a payment provider to handle the payments.

WHAT ACTUALLY HAPPENED (owner's account, 27 Nov 2026):
- Paystack DECLINED the activation request for Pulsify (ref 1799393, email dated
  24 Jun 2026). Their reason: the business falls outside their Acceptable Use Policy
  because it "results in or creates a significant risk of chargebacks, penalties,
  damages or other harm or liability". They said they have no flexibility.
- A second provider declined for the same reason. I referred to it as "PayShap", but
  PayShap is a bank payment rail, not a merchant gateway, so ask me to confirm which
  provider it was.
- How it was pitched (from memory, VERIFY in the repo/docs and lib/payouts.js): ticket
  money is collected into MY Paystack balance and held, then paid out to the event
  organiser or business AFTER the event. lib/payouts.js matches this: "paid tickets
  settle in full to Pulsify's Paystack balance (no split ...)" and payouts go out with
  Paystack Transfers.

Why this probably got rejected (researcher: confirm or reject each point with sources):
- Holding other people's money and paying it out later makes Pulsify a
  "payment facilitator / aggregator". If an event is cancelled or flops, every buyer
  charges back against MY merchant account, and providers see a new solo business
  as unable to cover that.
- Event ticketing is a "future delivery" business (paid now, delivered weeks later).
  Card schemes and gateways rate that as high risk on its own.
So simply switching providers with the same pitch will probably get the same answer.

Researcher: find a model that providers WILL approve. Options to investigate (not
decisions):
  A. Split the business in two. Apply first ONLY for the low-risk part: the R220/R360
     monthly SaaS subscriptions for organisers and businesses. Software subscriptions
     are a normal, low-chargeback category. That gets revenue flowing now.
  B. Tickets where the ORGANISER is the merchant of record. Money goes straight to the
     organiser's own account and Pulsify only takes a fee, so Pulsify never holds the
     funds. Which SA providers support split payments / sub-accounts / connected
     merchants for this (e.g. Peach Payments, Yoco, PayFast, Ozow, Stitch, iKhokha)?
     What does each organiser need in order to onboard?
  C. Tickets with reduced risk on Pulsify's side: rolling reserve, delayed payouts,
     refund guarantee, payouts only to verified organisers, a clear refund policy.
     Which providers accept this, and what do they need (CIPC registration, trading
     history, etc.)?
  D. Partner with an established SA ticketing provider that already has gateway
     approval (Pulsify does discovery, they process tickets) as a stop-gap.
For each option: which providers, requirements, fees, how much of the existing Paystack
code can be reused, and the realistic approval odds for a new solo business.
Also check whether Paystack will reconsider an application that covers ONLY option A.

The researcher can start Phase 2 research while Phase 1 is being built, because it
doesn't touch code.

Researcher: compare the realistic South African options. At least: Paystack (current),
Yoco, PayFast (Network International), Ozow, Peach Payments, iKhokha, Stitch, and
any other that fits. For each one, with source links and dates:
- Will it onboard a small/new business or sole proprietor? Exact documents required
  (CIPC registration, bank account, ID, proof of address, website requirements such as
  terms, refund policy and contact details).
- Does it allow a MARKETPLACE / ticketing model (taking money for events run by other
  organisers and paying them out)? This is often the real reason providers say no. Check
  for split payments, sub-accounts, or rules against collecting on behalf of third parties.
- Fees per transaction, payout timing, monthly costs.
- Recurring subscriptions supported?
- Developer API quality, webhooks, sandbox, and how much of the existing Paystack code
  could be reused.
- Approval time.
Also check what Pulsify itself needs to pass onboarding: are terms.html, a refund
policy, contact details and pricing visible on the site? List anything missing.

Output: a comparison table, a top recommendation with a runner-up, and a step-by-step
